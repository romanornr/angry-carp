# Phishing detection methods practical in TypeScript

Research date: 2026-09-22. Targeted primary-source review, not a systematic survey. It adds to the [design synthesis](phishing-detection-design.md), the [email-paper review](email-phishing-detection-papers.md), the [URL and visual review](url-and-visual-phishing-detection.md), the [Unicode evaluation](unicode-confusable-evaluation.md), and the [evidence options](phishing-evidence-options.md); papers already covered there are referenced, not repeated. Sources were read as abstracts and official project pages; numbers below are the ones stated there. No candidate visits, payloads, private mail, model calls, installs, or code were involved. Implementation-compatibility statements are marked **unverified** where no code was run.

## What Angry Carp already has

The current assessment path is: prepared email text plus operator notes, `lookup_rdap` (registrar, registration events, registrar abuse contacts) and `lookup_dns` (A/AAAA/NS/MX/TXT/CNAME with RCODE and truncation), then a model assessment that must separate observation from inference. Any new method has to add signal that this path does not already produce, or make an existing inference reproducible without the model.

## Methods compared

Email-level methods act on headers and body text the operator supplies. URL/page methods need the destination or its rendering, which Angry Carp does not fetch. "Offline" means computation over supplied evidence or previously retrieved records, with no new network request. DNS and RDAP acquisition remain network operations; the comparisons below can run locally once those observations exist.

### 1. Unicode/IDN and brand-lookalike domains (email-level, offline)

- **Chrome's IDN display policy** ([docs/idn.md](https://chromium.googlesource.com/chromium/src/+/main/docs/idn.md), read 2026-09-22) is the most concrete published rule set: show punycode when a label mixes scripts outside allowed combinations (Latin/Cyrillic/Greek never mixed; ASCII Latin only with CJK), when a label is digits plus digit spoofs, when it matches listed dangerous patterns, or when the registrable part's skeleton equals a top domain after diacritic removal. This is a policy, not an evaluated detector; Chrome publishes no false-positive rate for it.
- **ShamFinder** (Suzuki et al., IMC, 17 Sep 2019, [arXiv:1909.07539](https://arxiv.org/abs/1909.07539)) builds a homoglyph database automatically (glyph rendering similarity) rather than relying only on UTS #39 confusables, then measures IDN homographs in the wild. The abstract gives no accuracy figure; its contribution is the broader confusable table and the measurement, not a classifier.
- **Needle in a Haystack** (Tian et al., IMC 2018, [DOI 10.1145/3278532.3278569](https://dl.acm.org/doi/10.1145/3278532.3278569)) scanned five squatting types over 224 million DNS records, found 657K domains likely impersonating 702 brands, and verified 1,175 squatting phishing pages; more than 90% evaded popular blacklists for at least a month. Detection needed page content and OCR, so only its squatting-generation part is offline.
- **Combosquatting** (Kintis et al., CCS, 28 Aug 2017, [arXiv:1708.08519](https://arxiv.org/abs/1708.08519)): brand word plus extra tokens (`bifrostwalletapps`) rather than character swaps; 468 billion DNS records over almost six years; almost 60% of abusive combosquatting domains lived more than 1,000 days. This is the squatting type in the current case and the one UTS #39 skeletons cannot see.
- **dnstwist** ([github.com/elceef/dnstwist](https://github.com/elceef/dnstwist), read 2026-09-22) is the reference permutation engine (homoglyph, hyphenation, transposition, TLD swap, and other fuzzers). It generates candidates from a *known* brand domain; it does not classify an observed domain.

Plain TypeScript can implement: script detection per label with `\p{Script=…}` regex property escapes (ES2018, no dependency), a selected subset of Chrome's mixed-script checks, domain-form conversion, and brand-token containment or edit distance between the *claimed* brand's official registrable domain and each observed domain. A script regex alone does not implement Chrome's full UTS #39 policy. Domain decoding also needs an explicit runtime choice: WHATWG URL serialization and Node's `domainToUnicode` are different operations, and portable Unicode decoding remains unverified. A UTS #39 skeleton needs the `confusables.txt` data table; Node's built-in ICU does not expose `uspoof` to JavaScript (**unverified**: whether a maintained npm package ships a current table and runs in Workers). Flue only orchestrates: the check is a pure function over strings from the evidence and returns observations (`mixed_script`, `brand_token_in_other_domain`, `skeleton_match`), never a verdict.

False positives: legitimate multilingual domains and legitimate brand-plus-word domains (`bifrostwallet-support`, regional resellers). The signal is only meaningful relative to an official domain the operator supplies in notes; guessing the official domain from memory reintroduces model hallucination.

### 2. URL and domain lexical/structural signals (email-level for the literal URL, offline)

- **URLNet** and the visual detectors are already reviewed in [url-and-visual-phishing-detection.md](url-and-visual-phishing-detection.md). What that review does not cover is the cheaper structural family: registration-time and infrastructure features.
- **Registration age relative to receipt** is already available from `lookup_rdap` events. In the current case both domains were registered within 36 hours of the email. The literature that quantifies registration-time abuse prediction (**PREDATOR**, Hao et al., CCS 2016, DOI 10.1145/2976749.2978317; **COMAR**, Maroofi et al., EuroS&P 2020) was not re-verified this session (publisher pages blocked scripted access), so no figures are quoted; they are listed as reading, not evidence.
- **Blacklist lag** is the practical finding: Needle's >90% evasion for at least a month means reputation feeds are late for exactly the fresh domains Angry Carp sees; a local age-plus-lookalike rule is not redundant with them.

Plain TypeScript can implement: `receiptTime − registrationEvent` in days from the RDAP result, "sender registrable domain ≠ action-link registrable domain", and "link host is a proxy/CDN range" only once IP ownership is available (deferred). A public-suffix list is needed to compute registrable domains correctly (**unverified**: bundle size and Workers compatibility of `psl`/`tldts`); without it the rule must use the operator-supplied registered domain as today.

False positives: new legitimate businesses, product-launch domains, transactional subdomains on ESPs.

### 3. Header, authentication, and relationship signals (email-level; offline for headers, mailbox-dependent for relationships)

- **Weak Links in Authentication Chains** (Shen et al., USENIX Security 2021, [page](https://www.usenix.org/conference/usenixsecurity21/presentation/shen-kaiwen)) identifies attacks bypassing SPF, DKIM, DMARC and UI protections, including combined "cocktail" attacks; 30 email services and 23 clients tested, all vulnerable to some new attack. Consequence for Angry Carp: a `pass` in Authentication-Results is necessary context, not exculpatory, and header parsing must check *alignment* (RFC 7489: `From` domain versus DKIM `d=` and SPF domain) and multiplicity (more than one `From`, `Sender` tricks) rather than reading the first `pass`.
- **Detecting Credential Spearphishing in Enterprise Settings** (Ho et al., USENIX Security 2017, [page](https://www.usenix.org/conference/usenixsecurity17/technical-sessions/presentation/ho)): features from sender reputation and first-contact history plus non-parametric anomaly scoring over 370 million emails; detected 6 known successful campaigns (missing one), 9 failed, 2 previously unknown, at a false-positive load of under 15 analyst minutes per month. Its relationship features need mailbox history Angry Carp does not have; the lateral-phishing paper in the earlier review has the same dependency.
- RFC 8601's `authserv-id` rule (trust only the receiving system's Authentication-Results) is already in `phishing-triage.md`.

A TypeScript parser could extract Authentication-Results and compare documented authenticated identifiers with the visible From domain. This would interpret supplied authentication observations, not reverify SPF or DKIM. Preserve method-specific fields: DKIM alignment uses the signing `d=` domain, not a generic identity field. Strict and relaxed alignment also differ; relaxed alignment needs an organizational-domain policy. See [RFC 7489 §3.1](https://www.rfc-editor.org/rfc/rfc7489.html#section-3.1).

Receiver trust must be supplied or established outside the header parser. Neither an `authserv-id` string nor a position in the Received chain proves trust. Missing or untrusted authentication evidence must produce an unknown result, rather than `aligned: false`. See [RFC 8601 §7.1](https://www.rfc-editor.org/rfc/rfc8601.html#section-7.1). Synthetic headers can test parsing and these distinctions. Relationship signals are out of scope until a mailbox connector exists.

False positives: legitimate ESP sending (DKIM `d=` on the customer domain with SES/Resend infrastructure passes and is aligned, exactly like the current case), forwarded mail breaking SPF.

### 4. Semantic contradiction and brand/action matching (email-level; model-dependent)

- **ChatSpamDetector** (Koide et al., 28 Feb 2024, rev. 23 Aug 2024, [arXiv:2402.18093](https://arxiv.org/abs/2402.18093)) prompts GPT-4 with the email and reports 99.70% accuracy on "a comprehensive phishing email dataset"; the abstract names neither the dataset nor a temporal split. **E-PhishGen** (Pajola et al., 1 Sep 2025, [arXiv:2509.01791](https://arxiv.org/abs/2509.01791), already reviewed) is the corrective: same-corpus scores do not transfer across corpora. Treat 99.7% as a ceiling on one distribution, not an expectation.
- **PhishAgent** (Cao et al., 20 Aug 2024, rev. 23 Jan 2025, [arXiv:2408.10738](https://arxiv.org/abs/2408.10738)) combines offline and online knowledge bases with a multimodal LLM for brand recognition from logos and HTML. It is a page-level method needing the rendered page and web search; not offline.
- The **Bifrost** reasoning in the current case (official support article says no desktop app exists; email offers one) is a contradiction check between the claimed brand's own statement and the requested action. No reviewed paper evaluates this as a standalone email-level method; it is an LLM-assisted step here, and its value depends on the operator supplying the official statement as evidence rather than the model recalling it.

What Flue orchestrates: a first model call restricted to structured extraction (`claimedBrand`, `requestedAction`, `artifactType`, `officialDomainFromNotes`) as JSON, then TypeScript rules over that JSON plus lookup results. Untrusted input applies twice: the email can attempt prompt injection (LLMail-Inject, already reviewed), and the extraction output must be treated as an inference, not an observation. Keeping the extraction call tool-less limits what an injected instruction can do.

## Cross-cutting limits

- **Temporal and dataset leakage.** Arp et al., *Dos and Don'ts of Machine Learning in Computer Security* (USENIX Security 2022, [arXiv:2010.09470](https://arxiv.org/abs/2010.09470)) surveyed 30 top-tier papers over 10 years and found design/evaluation pitfalls widespread, showing empirically how they inflate results. Angry Carp trains nothing, but evaluation pitfalls still apply. These include rules tuned on their evaluation cases, duplicate campaigns, unrepresentative samples, misleading aggregate accuracy, and uncertain historical labels. Prior model verdicts and provider acknowledgements are not ground truth, per the existing evaluation protocol.
- **Multilingual.** Script observations do not require a brand reference; brand comparisons do. Test both against legitimate multilingual domains rather than treating non-Latin text as suspicious by itself. E-PhishGen's multilingual benchmark is the only reviewed source with non-English email evaluation.
- **Untrusted input.** Every method above consumes attacker-controlled strings. Deterministic checks must bound input size and character classes the same way `lookup_dns` does; model steps must be tool-less and their outputs labeled as inference.
- **Incremental value over RDAP/DNS plus LLM.** Method 1 and the age/alignment parts of 2 and 3 make inferences the model currently draws in prose into reproducible observations with sources. Method 4 does not add signal beyond the current assessment; it adds structure and testability. Page-level methods add signal only with a fetch the policy forbids.

## Two next experiments (public or synthetic data only)

Implementation update, 2026-09-22: the first capability is now a bounded [local domain comparison tool](../domain-lookalikes.md). Its shipped scope is skeleton equality, literal and skeleton identifying-label containment, and primary-script inventories with explicit limits. The broader experimental recommendations below remain research proposals.

1. **Lookalike and brand-token observations.** A pure TypeScript function taking `{ officialDomain, observedDomains[] }` and returning per-domain observations: script mix per label (a documented subset of Chrome-inspired checks), punycode/Unicode forms, brand-token containment, and Damerau-Levenshtein distance to the official registrable domain. Inputs: the 13 synthetic pairs from the Unicode evaluation, dnstwist-style permutations generated in TypeScript for three public brand domains, and a control set of legitimate IDN and brand-plus-word domains chosen from public registries. Report which controls trigger; no verdicts, no model. Skeleton matching is added only if a confusables table proves loadable (**unverified**).
2. **Authentication alignment and registration-age observations.** A parser for `Authentication-Results`, `From`, and `Received`, with an explicit trusted-receiver configuration, producing aligned, unaligned, or unknown observations and their source fields. Combine an established receipt time with existing RDAP events into `daysBetweenRegistrationAndReceipt`; retain missing or inconsistent dates as gaps. Inputs: synthetic header sets covering ESP-aligned legitimate mail, forwarded mail, spoofed multiple-From cases from the Weak Links taxonomy, and the current case's public facts. Report the observation table and which legitimate synthetic cases would have looked suspicious. Then, separately approved, run the triage prompt on the same synthetic emails with and without these observations in the notes and compare whether the Checks-and-gaps section becomes more specific.

Neither experiment changes the runtime, adds a tool, or touches private evidence. If both produce observations the operator finds useful, the next design question is whether they become Flue tools (like the lookups) or prepared-evidence enrichers run before the assessment; that is not decided here.
